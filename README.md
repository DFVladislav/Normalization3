# Лабораторная работа № 3: нормализация данных до 3НФ

Практическая работа на MySQL в Docker: аномалии в плоской таблице «сотрудники — отделы — продажи», разложение данных на три связанные таблицы, проверка переноса, резервные копии и журнал SQL-действий.

Выполняется в связке **VS Code — Git Bash — Docker CLI** (контейнер `my-mysql`, пароль root `123`).

## 1. Что нормализуем

Исходная таблица из задания хранит в одной строке сразу данные сотрудника, его отдела и продаж за месяц:

| Код сотрудника | Имя сотрудника | Месяц | Продажи | Код отдела | Название отдела |
|---:|---|:---:|---:|---:|---|
| 1 | Иванов Иван | 2026-01 | 150000 | 10 | Отдел реализации |
| 1 | Иванов Иван | 2026-02 | 180000 | 10 | Отдел реализации |
| 2 | Петров Пётр | 2026-01 | 120000 | 10 | Отдел реализации |
| 2 | Петров Пётр | 2026-02 | 135000 | 10 | Отдел реализации |
| 3 | Сидорова Мария | 2026-01 | 90000 | 20 | Отдел развития |
| 3 | Сидорова Мария | 2026-02 | 105000 | 20 | Отдел развития |
| 4 | Козлова Анна | 2026-01 | 220000 | 30 | Отдел экспорта |
| 5 | Смирнов Олег | 2026-01 | 110000 | 30 | Отдел экспорта |

Потенциальный ключ строки — `(employee_id, sales_month)`. Функциональные зависимости:

- `employee_id → employee_name, department_id`
- `department_id → department_name`
- `(employee_id, sales_month) → sales`

Нарушения нормальной формы:

- **1НФ** — в макете «Название отдела» было списком из трёх значений (повторяющаяся группа); после развёртывания в строки поля атомарны, но значения дублируются.
- **2НФ/3НФ** — `department_name` зависит не от ключа строки, а транзитивно: `employee_id → department_id → department_name`.
- **Аномалии**: переименование отдела требует правки всех его строк; новый отдел нельзя завести без сотрудника с продажами; удаление строк сотрудника стирает и данные об отделе.

`employees_bad` намеренно не имеет первичного ключа и ограничений `NOT NULL` — так нагляднее показывать недостатки исходной структуры.

## 2. Схема 3НФ

| Таблица | Первичный ключ | Что хранит |
|---|---|---|
| `departments` | `department_id` | Код и название отдела |
| `employees` | `employee_id` | Сотрудник и ссылка на отдел |
| `employee_sales` | `(employee_id, sales_month)` | Продажи сотрудника за месяц |

В `employees` отдел задаётся внешним ключом на `departments`, в `employee_sales` сотрудник — внешним ключом на `employees`. Каждый атрибут зависит от ключа своей таблицы, от всего ключа и не транзитивно — схема в 3НФ.

## 5. Демонстрация аномалий

```bash
docker exec -i -e MYSQL_PWD=123 my-mysql mysql -uroot --table --default-character-set=utf8mb4 < sql/02_anomalies.sql
```

- **Обновление:** отдел 10 встречается в 4 строках; переименование требует обновить все строки. Частичное обновление даёт противоречие — у одного отдела два названия:

```
+---------------+---------------------------------+-----+
| department_id | department_name                 | cnt |
+---------------+---------------------------------+-----+
|            10 | Отдел реализации                |   2 |
|            10 | Отдел продаж                    |   2 |
|            20 | Отдел развития                  |   2 |
|            30 | Отдел экспорта                  |   2 |
+---------------+---------------------------------+-----+
```

- **Вставка:** новый отдел нельзя добавить без сотрудника с продажами — появляется строка-мусор с `NULL`:

```
+-------------+---------------+-------------+-------+---------------+---------------------------------+
| employee_id | employee_name | sales_month | sales | department_id | department_name                 |
+-------------+---------------+-------------+-------+---------------+---------------------------------+
|        NULL | NULL          | NULL        |  NULL |            40 | Отдел маркетинга                |
+-------------+---------------+-------------+-------+---------------+---------------------------------+
```

- **Удаление:** удаление строк отдела 20 стирает и саму информацию о нём — оба контрольных запроса возвращают пустое множество (`Empty set`).

Каждая пробная операция выполняется в транзакции и отменяется `ROLLBACK`, поэтому финальная выборка показывает исходные 8 строк без изменений.

## 6. Дамп до нормализации

Лог временно выключается, чтобы служебные запросы `mysqldump` не попали в журнал действий:

```bash
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'OFF';"
docker exec -e MYSQL_PWD=123 my-mysql mysqldump -uroot --set-gtid-purged=OFF --single-transaction staff_norm > dump_before.sql
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'ON';"
ls -lh dump_before.sql
```

В `dump_before.sql` — только исходная таблица `employees_bad` с данными.

## 7. Нормализация до 3НФ и перенос данных

```bash
docker exec -i -e MYSQL_PWD=123 my-mysql mysql -uroot --table --default-character-set=utf8mb4 < sql/03_normalize.sql
```

Скрипт создаёт три таблицы с ключами и внешними ключами и переносит данные командами `INSERT ... SELECT DISTINCT`:

```
+----------------+----------+
| table_name     | rows_cnt |
+----------------+----------+
| departments    |        3 |
| employees      |        5 |
| employee_sales |        8 |
+----------------+----------+
```

Исходная таблица пока не тронута.

## 8. Проверка данных и аномалий

```bash
docker exec -i -e MYSQL_PWD=123 my-mysql mysql -uroot --table --default-character-set=utf8mb4 < sql/04_check.sql
```

Контрольные значения вывода скрипта:

- Суммы `SUM(sales)` до и после совпадают: **1 110 000.00**, строк **8** и **8**.
- Сотрудников и строк `employees`: **5** и **5**; отделов и строк `departments`: **3** и **3**.
- `missing_from_3nf = 0` и `extra_in_3nf = 0` — ничего не потеряно и не добавлено лишнего.
- Соединение трёх таблиц восстанавливает исходные строки один в один.
- Тестовые запросы: отделы по сумме продаж (реализация 585 000.00, экспорт 330 000.00, развитие 195 000.00), лучший сотрудник — Иванов Иван (330 000.00), итоги за январь 690 000.00 и февраль 420 000.00, сотрудник 3 — Сидорова Мария, «Отдел развития».

Только после этих проверок скрипт переименовывает исходник: `RENAME TABLE employees_bad TO employees_bad_archive` (данные не удаляются). Итоговый список таблиц:

```
+-----------------------+
| Tables_in_staff_norm  |
+-----------------------+
| departments           |
| employee_sales        |
| employees             |
| employees_bad_archive |
+-----------------------+
```

## 9. Дамп после нормализации

```bash
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'OFF';"
docker exec -e MYSQL_PWD=123 my-mysql mysqldump -uroot --set-gtid-purged=OFF --single-transaction staff_norm > dump_after.sql
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'ON';"
```

В `dump_after.sql` — три нормализованные таблицы и архив `employees_bad_archive`.

## 10. Экспорт только SQL-действий этой работы

Остановите журналирование и скопируйте выделенный файл из контейнера:

```bash
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'OFF';"
docker cp my-mysql:/var/lib/mysql/normalization3_20261118.log ./general_raw.log
```

Отфильтруйте записи соединений и служебные запросы клиента (скрипт сохраняет многострочные SQL-запросы):

```bash
python sql/filter_log.py general_raw.log my_actions.log
rm general_raw.log
```

Получается 178 строк — только SQL-действия этой работы: от `CREATE DATABASE staff_norm` до `SHOW TABLES`, включая транзакционные демо аномалий (`SET autocommit = 0` … `ROLLBACK`). Служебные запросы `mysqldump` и команды переключения лога в файл не попадают.

## 11. Файлы задания

- `sql/01_create_bad.sql` — создание базы `staff_norm` и исходной таблицы.
- `sql/02_anomalies.sql` — три транзакционные демонстрации аномалий.
- `sql/03_normalize.sql` — схема 3НФ и перенос данных.
- `sql/04_check.sql` — проверки и архивирование исходника после проверок.
- `sql/filter_log.py` — экспорт только SQL-действий из общего лога.
- `dump_before.sql`, `dump_after.sql` — дампы до и после нормализации.
- `my_actions.log` — отфильтрованный лог действий.
